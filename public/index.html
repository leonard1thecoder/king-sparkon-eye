Identity verification · Developer infrastructure

Face-based identity verification.
Built for your platform.

King Sparkon Eye is an integration-agnostic identity verification platform foundation. The current Rust service validates images and runs YuNet face detection; tenant-isolated identity lifecycle, face matching, scoped identification and asynchronous verification remain in development. Integrating applications retain ownership of their users, permissions, consent capture and business workflows.

01 / Platform capabilities

One tenant. One explicit scope. A result the application controls.

The target platform separates tenant-owned identity data, face-only processing and application-owned decisions. Matching, scoped identification and asynchronous sessions are roadmap capabilities, not shipped API behavior.

01 — TENANT

Resolve tenant context

The target API resolves tenant authority from validated credentials, never from an untrusted caller-supplied identifier.

02 — CAPTURE

Submit a face capture

The integrating application owns capture, purpose selection and consent. Eye validates image input.

03 — VERIFY

Process within scope

Face-only 1:1 matching and explicit tenant-local 1:N identification are target capabilities; the current service only assesses photos and detects faces.

04 — DECIDE

Keep the decision external

The integrating application interprets the probabilistic result and retains ownership of its permissions and business workflow.

03 / Implementation status

A working service foundation. Not yet a complete identity API.

The status below distinguishes current Rust behavior from the approved multi-tenant identity platform roadmap.

Implemented today

  • Rust/Axum HTTP service and health probes.
  • Authenticated, bounded image ingress and photo assessment.
  • YuNet face detection through ONNX Runtime.
  • Account pages and authentication routes, excluded from search indexing.

Roadmap — not shipped

  • Tenant isolation, tenant API credentials and identity lifecycle.
  • Face embeddings, 1:1 matching and tenant-scoped 1:N identification.
  • Durable asynchronous verification sessions and signed webhooks.
  • Calibrated recognition behavior based on consented evaluation data.

Photo assessment is synchronous and does not enroll an identity or create a verification session. A detector result is not identity verification. No liveness or legal-identity proof is claimed.

04 / Security & privacy

Privacy boundaries are part of the platform contract.

The target architecture is face-only and tenant-isolated. The current service is still a limited photo-assessment foundation; do not infer a complete biometric lifecycle from the roadmap.

01 / Isolation

Tenant-scoped by design

Identities, templates, scopes, sessions, results and evidence must never be shared across tenants. Tenant isolation and machine credentials remain implementation work.

02 / Face-only

Probabilistic results

Face similarity is not proof of legal identity, liveness, consent or authorization. Recognition models and thresholds require implementation and consented evaluation.

03 / Data lifecycle

Clear ownership

Integrating applications own consent capture and business purpose. Evidence retention, deletion and audit controls are being defined; no unsupported compliance claim is made.

The current photo-assessment endpoint reports persistence: NOT_REQUESTED. It does not create an identity or store a face template. Read the implementation and security status before integrating.
